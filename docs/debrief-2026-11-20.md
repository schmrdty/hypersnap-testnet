## Findings, including the ones against me

### 1. A one-validator chain is silently broken from block 1 (upstream bug)

For 4,499 blocks the single genesis validator proposed every block with an empty
shard witness list and committed it, because a lone validator never validates its own
proposals. The moment a second validator validated one, the block shard halted for
good: there were no stored witnesses to continue from, and no restart can add them.
I read the stored blocks over gRPC to confirm it: block 100 and block 4,499 carry the
same hash of an empty list.

What I did: regenesis with two validators in the genesis set, which produces real
witnesses from block 2 (verified over gRPC), and an upstream report with the code path
(`collect_confirmed_shard_witnesses` in `src/consensus/proposer.rs`). The RFC's
"two validators at genesis" rule exists because of this. Cost: a four-hour chain with
one throwaway account.

### 2. I halted my own chain with `restart` instead of `up -d` (my mistake)

For the first set change I gave the read node its key and the validator compose file,
then ran `docker compose restart`. That restarts the existing container with the
environment it was created with, so the node never received the key. At height 4,500
the set became two keys with one signer present, and one signer cannot reach two
thirds. The chain sat at 4,499 for about 80 minutes until I recreated the container.

What I changed: the runbook says it in one line now (a network-file change needs
`restart`; a compose or `.env` change needs `up -d`), `join.sh` writes the key before
the first start so a joining validator cannot hit this, and the finding itself is
useful: a set change with an absent member halts the chain at the height and resumes
when the member appears.

### 3. The removal rehearsal passed for the wrong reason (recorded, not hidden)

I announced the removal at height 7,700 and restarted all three nodes at about 8,084,
after the height. It worked only because every node was late by the same amount and
switched together. In operation, one node late while the others are on time is the
halt case from finding 2. The record says so; I am not counting this as a clean pass.
The 48-hour notice in the RFC is there so nobody has to be as fast as I was pretending
to be.

### 4. My monitoring made the testnet look involved in a mainnet halt (my bug)

When mainnet halted on 11-19 at 01:00 UTC, the stall table on my health page showed
"testnet-0" in a column headed "Peer" on every mainnet row. Several people, reasonably,
read that as the testnet being peered with mainnet validators. The column was never a
gossip peer: it was the node the detector compared against to confirm that time was
passing, and since the testnet was added it had the lowest block delay and won that
pick.

What I did the same night: fixed the detector so a mainnet stall is only ever compared
against another non-testnet network, renamed the columns to "Compared with" and "Its
height", shipped it, and verified it on the next mainnet-wide stalls. Then I checked
the actual question on the testnet server itself: 72 hours of logs across every
container contain zero mentions of any mainnet validator, of my mainnet read node's
VPS, or of the Snapchain bootstrap nodes, and conntrack shows zero live flows to them.
Each testnet node binds its own UDP port (3382, 4382, 5382), so multiple Docker projects
could not fighting over a port. Independently of my logs: the node binary accepts a 
discovered peer only when its identify protocol matches its own network, and no testnet 
key is in mainnet's validator set, so a testnet message could not carry a mainnet vote 
even if delivered.

The lesson I am keeping: a monitoring page that other operators read during an
incident has to be unambiguous before the incident, not after.

### 5. The testnet has a single point of failure, and it is me

Both validators run on one server I operate. If that server goes down, the testnet
halts. With four validators one can be down; until then every outage is mine. Three
days after the call, no operator has filed an issue. I am stating that plainly rather
than letting the uptime number imply a resilience the setup does not have.

## What I am asking for

Unchanged from the RFC, and more urgent than it reads there:

1. Two validators from operators other than me. With four, the chain survives one
   being down. 4 vCPU, 8 GB RAM, 100 GB SSD, static IPv4, UDP 3382 and TCP 3381 open.
2. Read nodes. 2 vCPU, 4 GB, 50 GB. You get a testnet API for your own client.

Join: `git clone https://github.com/schmrdty/hypersnap-testnet`, `./join.sh validator`
or `./join.sh readnode`, then open an operator issue with your public IP, peer id, and
for validators the consensus public key the script printed. Never the private key, the
`.env`, or the `.pem`.

Policies stand: stable `latest` image, nightly windows announced with a start and an
end, resets with seven days notice, set changes as pull requests with the height in the
title and 48 hours of notice.

Health page: https://snapdiff.schmidtiest.xyz/?net=testnet. RFC:
https://github.com/schmrdty/hypersnap-testnet/issues/1. Questions and corrections in
the repository issues; if something in this debrief is wrong, open one and I will fix
the record.
